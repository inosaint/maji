# Brand Pipeline

Turns "design a brand called X" (optionally: "as a rebrand of `<reference-url>`") into five concrete, reviewable artifacts, built one at a time by a single long-lived orchestrator agent **dedicated to that one brand**.

## When to use this

The user wants to take a brand — invented from scratch, or a rebrand of a real, existing site — through: a positioning brief, a visual-direction moodboard, a mocked-up homepage informed by category research, an extracted design-token/component system, and a short animated launch teaser. This works inside any repo organized as a multi-brand playground (a `brands/<name>/` folder per brand, a root hub linking to each), but the five-stage thinking applies regardless of the surrounding repo's exact shape — adapt the output paths if the convention differs.

## The five stages

Each stage produces one artifact and **stops**. Do not run more than one stage without the user reviewing and explicitly approving the previous one — this is the whole point of the pipeline: stage *N* is informed by what was decided in stage *N-1*, so skipping ahead defeats it.

1. **Brief** — positioning statement, target audience, and a tone keyword (or short phrase) that will discipline every later visual decision. If rebranding a real site, ground this in what the site actually says about itself (fetch it, read its actual copy/structure — don't invent a positioning that contradicts the source). Output a single self-contained HTML page: masthead + a few structured "brief cards" (positioning / audience / tone keyword).
2. **Moodboard / directions** — 2–3 visual directions, each with a color swatch strip (with hex values and role labels: background/surface/ink/accent/etc.), **2–3 real, genuinely distinct type-pairing options** per direction (not one pairing repeated at different weights — actual different typeface choices, real Google Fonts, rendered live with a heading + body specimen each, not just named), and a short prose description of the imagery/texture direction (no image-generation tool is assumed available — describe the visual language in words, don't fake photography).

   "Genuinely distinct" means spanning real type *categories*, not just picking different names within the same one — a known failure mode is proposing e.g. three different geometric sans / literary-serif pairings across three directions and calling that wide exploration. Before finalizing, check the options span at least: a serif with real presence (editorial, slab, or humanist — pick what fits the brand, but pick one), an alternative sans in a different register than the anchor font itself (if the real site's font is geometric, try humanist or grotesk, not another geometric), and something with more character for display/hero moments than either. Only include a mono if the content actually has a reason for one (data, specs, code, timestamps) — don't default to it.

   If the brand already has a real identity (a rebrand): **anchor the color palette** to what's actually on the live site — pull real hex values out of its CSS, don't invent new ones. **Do not anchor type the same way** — the site's current font choice is only *one* legitimate option to include among the 2–3 alternatives per direction, not something to lock in and repeat. Type selection stays a real, open choice even when color doesn't (see the "Hard rules" section — conflating these two is a known failure mode).

   If the brand is invented from scratch, both color and type can diverge freely across directions.

   **User-supplied reference images and assets**: this is a required interactive checkpoint between Stage 1 and Stage 2, not a passive folder that might get used if the user happens to remember it. The moment Stage 1 (Brief) completes: create `brands/<name>/research/inspiration/`, **open/reveal it** (e.g. `open <path>` on macOS) so it's actually visible, and **explicitly ask the user** (in chat) to drop in anything relevant before Stage 2 starts — an existing logo or wordmark file, brand marks, product photos, mood/reference images, competitor screenshots, anything visual they already have. Wait for their response (either images added, or an explicit "nothing to add, go ahead") before starting Stage 2 — don't silently proceed after some fixed delay or assume an empty folder means done.

   Once given the go-ahead: check the folder for anything that was added. If it has images, read/view each one directly (the file-read tool supports images) and let them genuinely inform the directions — not just a token mention. Concretely: name what stands out in each reference (a color relationship, a type treatment, a layout density, a texture/material quality, a mood, or — if it's an actual logo file — the mark itself as something later stages may need to incorporate or reference), fold that into the relevant direction's prose imagery description, and where it's a real color/material reference (not just a mood/vibe image), let it influence the actual swatch values too, not just the text. If the user explicitly said there's nothing to add, note that in the moodboard's brief intro and proceed from the brief/research alone.
3. **Explorations / mockup** — before building, research 2-4 comparable sites in the same category (via web search/fetch) for layout and UX pattern grounding — what does a good site in this category actually do structurally? Then build the real homepage mockup(s) for the chosen direction(s): a fully self-contained HTML page applying the direction's actual palette/type, with real (or realistic placeholder) copy, not lorem ipsum. If multiple directions are being compared, build one mockup per direction and a small tab-switcher hub page that iframes between them.

   Every mockup must be **mobile-friendly**, not desktop-only: responsive breakpoints, a working mobile nav (not just a desktop nav that overflows), and readable type/spacing at small widths — this is a hard rule (see below), not optional polish to add later.

   If a direction resolves to a **light + dark pair** rather than one fixed palette, don't ship it as two separate mockup files to flip between — bake both modes into the *same* page: CSS custom properties per role (not per literal color), a `prefers-color-scheme: dark` media query as the default/system-driven mode, `:root[data-theme="dark"]` / `:root[data-theme="light"]` overrides that win over the system default, and a manual toggle control (place it in the footer unless told otherwise) that flips `data-theme` and persists the choice (e.g. `localStorage`). One real page that actually themes, not two static snapshots side by side.
4. **Design system** — once a direction/mockup is confirmed, generalize it into reusable tokens (colors, typography, spacing/radii/shadows as JSON) and components (button, badge, input, data table, dialog — or whatever the mockup actually uses) as JSON, plus a showcase page rendering them. Derive every token from what's *actually used* in the confirmed mockup — don't reuse another brand's token values or invent new ones not grounded in the mockup.
5. **Teaser** — a short, self-contained animated HTML/CSS/JS page: a launch teaser/promo sequence (e.g. logo reveal → tagline → a palette/type flash → a hero beat), auto-playing, no user interaction required. This stands in for a "launch video" — there is no video-rendering tool available, so the teaser is browser-native motion, not a rendered video file. Say so explicitly when presenting this stage, don't let the user assume they're getting an `.mp4`.

## How to run it: orchestrator-agent pattern

Don't drive this by calling a fresh subagent per stage — a fresh agent has no memory of prior stages and forces you to re-explain everything each time. Instead:

1. Gather the brief inputs first (brand name, reference URL if this is a rebrand, any explicit user constraints — e.g. "homepage only," "anchor to the real identity," specific stage-2 direction count). If rebranding a real site, fetch it yourself before spawning the orchestrator, so the orchestrator's first message already contains the real palette/type/copy rather than having to go re-fetch it.
2. Spawn **one new orchestrator agent per brand** (general-purpose) with a prompt containing: the full brief inputs above, the five-stage definitions from this skill, the explicit instruction to build **only stage 1** and then stop, and — critically — the instruction that it must stop and report after every subsequent stage too, never chaining two stages in one turn. **Never resume a different brand's orchestrator to start a new brand's pipeline** — even though it's tempting once one is already running, its context is soaked in the prior brand's structural choices (layout shapes, section conventions, component patterns) and those bleed into the new brand's output even when the color/type/content are correctly kept separate. A brand-new brand gets a brand-new orchestrator, full stop.
3. When the orchestrator reports a stage's output, **open every HTML file it produced in that stage** (e.g. `open <path>` on macOS) so it's actually visible, not just described — do this yourself in the driving session immediately after each stage completes, don't wait to be asked. Then review it and relay a summary to the user. Wait for explicit approval or direction before continuing.
4. To continue, resume the **same** orchestrator agent (by name/id, via a message) with the next stage's go-ahead plus any corrections from the review. Do not spawn a new agent per stage — the whole value of this pattern is that the orchestrator accumulates the full pipeline history in its own context.
5. If the user wants to redirect mid-stage (change a color, swap a font pairing, adjust scope), send that as a message to the same orchestrator rather than restarting the stage from a fresh agent.

## File conventions (adapt to the repo's actual layout)

In a `brands/<name>/` multi-brand repo, following the pattern already established for other brands in this repo:
- `brands/<name>/research/brief.html`, `moodboard.html`, `explorations.html`, `mockups/*.html`
- `brands/<name>/tokens/*.json`, `brands/<name>/components/*.json`, `brands/<name>/index.html` (the design system stage)
- `brands/<name>/research/teaser.html`
- `brands/<name>/research/inspiration/` — optional, user-supplied reference images for Stage 2 (see the Moodboard stage description). Create this folder proactively (with a placeholder note, e.g. "drop reference images here before Stage 2") when Stage 1 completes, so the user has an obvious place to add images before Stage 2 starts, rather than only reacting if they mention it.
- Every page is fully self-contained: inline `<style>`/`<script>`, Google Fonts via `<link>`, no build step.
- A stepper/topbar convention across all five stage pages (done/active/upcoming states, linking between stages) helps the whole flow feel navigable end-to-end — see `brands/memlab/research/*.html` and `brands/memlab/index.html` in this repo for a fully worked example of this convention, including the JSON token/component schema shape used in stage 4.
- If the repo has a root hub (`brands.json` + a viewer `index.html`), register the new brand there once stage 1 exists, and keep it pointed at whatever the current furthest completed stage is.

## Hard rules

- Never run two stages in the same turn without a review in between.
- Never fabricate a rebrand's positioning or palette — fetch and read the real source before stage 1 if a reference URL is given.
- Never claim to produce a video; the teaser stage is animated HTML/CSS/JS.
- Keep the orchestrator agent alive across the whole run — resume it, don't replace it.
- Open every HTML file a stage produces (e.g. `open <path>`) as soon as that stage completes — don't just report the path, actually show it.
- In a rebrand, anchoring to the real identity applies to *color*, not *type*. Never collapse a direction's "2-3 type options" into one typeface repeated at different weights just because the palette is anchored — type stays a genuine, comparable choice with real alternative typefaces even when color doesn't.
- Every page built from Stage 3 onward must be mobile-friendly: real responsive breakpoints and a functioning mobile nav, checked, not assumed.
- A confirmed light + dark direction gets built as one theming page (system-preference default + manual toggle that overrides it), never as two separate static mockup files.
- When scope is reduced (e.g. "homepage only" on a real multi-page site), don't wire the real site's other-page nav items (things like Sign In, a dedicated Exhibitions page, ticketing, etc.) to scroll-jack into an unrelated homepage section just to give them *something* to do — that misrepresents what's actually on the page. Only nav items that genuinely correspond to a section built on the page should be real in-page anchors; everything else should be an honest inert stub link, not a fake destination.
- Don't reuse the same small rotating set of typefaces across different brands' Stage 2 explorations (a known drift: Fraunces, Newsreader, Lora, Sora, Space Grotesk, IBM Plex, Inter, and Poppins keep reappearing regardless of brand). Google Fonts has thousands of options — pick per-brand based on that brand's actual register, not on what worked for a previous, unrelated brand in this same repo.
- One orchestrator agent per brand, never shared across brands. Resuming an existing orchestrator to kick off a *different* brand's pipeline causes structural bleed (layout shapes, section patterns, component conventions carried over from whatever it built before) even when color/type/content are kept correctly separate. New brand = new orchestrator, briefed fresh from that brand's own stage outputs.
- A mobile hamburger dropdown must overlay the page, not push it: give the menu `position: absolute; top: 100%; left: 0; right: 0;` with its own opaque background, anchored to the header (works for free if the header is already `position: sticky` — sticky elements are a positioning context for absolutely-positioned descendants). Leaving it in normal document flow (`display: block` inside the header on open) makes the header's own box grow/shrink every time the menu toggles, which reads as a layout bug even though the menu itself "works."
- Any element wrapping both plain nav links and `.btn`-classed links (e.g. a mobile menu's `<a>` styling meant only for the plain links) must scope its selector to exclude buttons — `.mobile-menu a:not(.btn)`, not `.mobile-menu a`. An element+class selector like `.mobile-menu a` (specificity 0,1,1) silently beats single-class component selectors like `.btn-primary` or `.btn` (0,1,0), overriding the button's color/padding/border regardless of source order. This is a general trap, not mobile-menu-specific: check any container-scoped `a` selector for `.btn` children before shipping.
- A `.wrap` (or any shared layout-utility class) used both as a bare container and combined with a component class on the same element (e.g. `class="wrap nav-row"`) needs care in media queries: a later media-query rule targeting `.wrap` alone will override *all* of the component class's own padding/margin shorthand at that specificity tier, not just add to it. Prefer editing the component class itself for component-specific spacing tweaks, or double check what else shares `.wrap` before changing it globally.
- Give every interactive element (nav links, mobile menu links, the hamburger toggle button itself) an explicit `:hover` state before calling a mockup's components "functional" — it's an easy thing to omit and easy to check for in one pass (`grep` for each interactive class and confirm a paired `:hover` rule exists).
